# AI求职面试助手面试题库

> 数据性质：本题库由公开面试准备资料、岗位能力要求、校园招聘常见问题、AI应用开发项目场景和模拟面试追问规则整理改写而成，用于应届生模拟面试与 RAG 问答演示。它不是真实企业面试原题记录，也不代表任何公司的官方题库。

## 1. 资料来源与使用说明

参考资料包括：

* NACE Career Readiness Competencies：用于提炼应届生通用能力，包括沟通、批判性思维、团队协作、技术能力、职业发展等。
* Amazon 官方面试准备资料：用于补充行为面试、STAR 方法、结构化表达和追问方式。
* Google Careers 等公开面试准备资料：用于补充候选人表达、问题拆解和岗位匹配思路。
* OpenAI Prompt Engineering 公开建议：用于补充 Prompt 设计、上下文组织、格式约束等 AI 应用开发考点。
* LangChain / LangSmith RAG 评估资料：用于补充 RAG 系统评估指标，如 answer relevance、answer accuracy、retrieval quality、groundedness。
* Azure AI Search、Weaviate 等向量检索与混合检索公开资料：用于补充 RAG 检索策略、关键词检索、向量检索、混合检索、metadata filter、rerank 等技术问题。

建议每个知识块控制在 300–800 字，字段中保留岗位、难度、问题类型、技能标签等 metadata，方便后续按岗位、技能和难度检索。

# 一、通用面试方法：STAR 与结构化表达

## 1.1 常见问题

1. 请介绍一次你解决复杂问题的经历。
2. 请讲一次你和团队成员意见不一致的经历。
3. 请讲一次你失败或结果不达预期的项目。
4. 请讲一次你在时间紧、资源少的情况下完成任务的经历。
5. 请讲一次你快速学习新工具或新业务的经历。
6. 请讲一次你主动发现问题并推动解决的经历。
7. 请讲一次你面对模糊需求时如何推进项目。
8. 请讲一次你接受反馈并改进结果的经历。
9. 请讲一次你在项目中承担责任但遇到困难的经历。
10. 请讲一次你说服他人接受你方案的经历。
11. 请讲一次你用数据支持决策的经历。
12. 请讲一次你从失败中总结经验并在后续项目中应用的经历。

## 1.2 答题结构

建议使用 STAR：

* Situation：背景是什么？
* Task：你的任务或目标是什么？
* Action：你具体做了什么？
* Result：结果是什么？有没有数据？你复盘了什么？

## 1.3 高质量回答标准

好的回答要做到：

1. 有具体场景，不要泛泛而谈。
2. 有个人贡献，不要只说“我们团队”。
3. 有量化结果，例如效率提升、错误率下降、用户数、完成周期、准确率、响应时间等。
4. 有复盘，说明后续如何改进。
5. 和目标岗位能力挂钩，例如 AI 应用开发岗位要突出技术实现、问题定位、工程落地和业务理解。

## 1.4 面试官追问

* 这个项目中你具体负责哪一部分？
* 如果再做一次，你会怎么优化？
* 你怎么证明这个结果是你的方案带来的？
* 有没有量化指标？
* 有没有遇到反对意见？你怎么处理？
* 这个经历体现了你什么能力？

1. 请介绍一下你的就业数据分析助手项目。

## 3.2 答题要点

回答项目时建议包含：

* 背景：求职信息分散，学生难以快速理解岗位、技能和就业趋势。
* 目标：做一个能查询就业数据、分析岗位趋势、辅助面试准备的 AI 助手。
* 技术：Python、SQL、Streamlit、RAG、Prompt、API 调用、可视化。
* 流程：数据采集/整理 → 清洗 → 结构化存储 → 文档切分 → Embedding → 向量检索 → Prompt 拼接 → 模型生成 → 页面展示。
* 个人贡献：数据清洗、SQL 查询、RAG 知识库、Prompt 模板、可视化页面、异常兜底。
* 成果：可以补充模拟指标，例如“将人工查找资料时间从 10 分钟缩短到 1–2 分钟”“测试问题命中率提升”“平均响应时间优化”等。不要编造真实上线数据，如果是模拟项目，要说明是测试集或演示环境数据。

7. 相似度阈值怎么确定？
8. 如何处理“没有检索到相关内容”的问题？

10. 如何保证回答结果与最新政策一致？
11. 如何做知识库更新？

## 3.4 典型回答：项目是不是只是调用 API？

可以回答：

> 我理解这个项目确实用到了大模型 API，但我认为 AI 应用开发的价值不只是调用 API，而是把模型能力嵌入到具体业务流程里。比如在这个项目中，我做了数据清洗、SQL 查询、RAG 知识库构建、Prompt 模板设计、异常处理和 Streamlit 页面展示。用户的问题并不是直接丢给模型，而是先通过检索找到就业数据或政策资料，再把上下文传给模型生成回答。同时我也做了兜底逻辑，比如检索为空时提示信息不足，API 超时时返回本地规则答案。所以这个项目体现的是从数据到模型再到应用展示的完整落地链路。

## 3.5 面试官追问

15. 如何评估 RAG 的效果？

## 4.2 答题要点

RAG 的标准流程：

1. 文档收集：政策、岗位、简历、面试题、行业报告等。
2. 数据清洗：去重、去噪、格式统一、字段规范化。
3. 文档切分：按段落、标题、语义边界切 chunk。
4. 向量化：使用 Embedding 模型把文本转成向量。
5. 存储索引：使用 FAISS、Chroma、Milvus、Pinecone、Weaviate 等。
6. 检索：用户问题向量化后召回 Top K 文档。
7. 上下文拼接：把检索内容、用户问题、输出要求放入 Prompt。
8. 生成回答：由大模型基于上下文回答。
9. 引用与校验：输出来源、判断是否有依据。
10. 评估与迭代：看召回率、准确率、groundedness、用户反馈。

## 4.3 进阶技术题

1. RAG 中如何处理长文档？
2. 如何避免 chunk 切断关键信息？
3. 如何给知识块添加 metadata？
4. 如何设计政策类文档的 metadata？
5. 结构化数据和非结构化文本如何结合？
6. SQL 查询结果如何和 RAG 检索结果一起进入 Prompt？
7. 什么时候用 SQL，什么时候用 Python？
8. 什么时候用关键词检索，什么时候用向量检索？
9. 如何实现混合检索？
10. BM25 和向量检索的区别是什么？
11. 如何做 rerank？
12. 如何设计召回评估集？
13. Recall@K、Precision@K、MRR、NDCG 分别适合评估什么？
14. 如何做回答质量评估？
15. 如何处理“最新政策”和“历史政策”的冲突？
16. 如何做灰度上线？
17. 如何做用户反馈闭环？
18. 如何监控 RAG 系统？
19. 如何降低响应延迟？
20. 如何降低 API 成本？

## 4.4 典型回答：Top K 怎么确定？

可以回答：

> 我不会凭感觉固定 Top K，而是会先构建一批测试问题，每个问题人工标注应该命中的文档，然后分别测试 Top K=3、5、8、10 时的 Recall@K、回答准确率和平均响应时间。如果 Top K 太小，可能召回不足；如果 Top K 太大，会增加上下文噪声和模型调用成本。比如在就业政策问答场景中，我会优先看 Recall@5 是否能覆盖关键政策文件，再结合回答准确率和延迟选择参数。如果 Top K=5 的召回率已经比较稳定，而 Top K=10 只带来很小提升但明显增加延迟，我会选择 Top K=5，并针对政策类问题增加 metadata filter，比如地区、发布时间和政策类型。

## 4.5 典型回答：如何降低幻觉？

可以回答：

> 我会从检索、Prompt、生成和评估四个层面降低幻觉。检索层面要保证知识库及时更新，使用相似度阈值、metadata filter 和 rerank 提高召回质量。Prompt 层面要求模型必须基于检索内容回答，如果资料不足就说明不知道。生成层面可以要求输出引用来源、区分“事实结论”和“推测建议”。评估层面则通过人工标注问题集，检查回答准确率、groundedness 和用户反馈。这样可以避免模型脱离资料自由发挥。

## 5.2 Prompt 设计要点

Prompt 模板通常包括：

* 角色：你是一个 AI 求职面试助手。
* 任务：根据用户简历、目标岗位和题库内容回答。
* 上下文：检索到的题库、简历信息、岗位要求。
* 约束：不得编造经历；资料不足时说明不足；数字必须来自数据。
* 输出格式：按“回答示例 + 答题逻辑 + 可优化点 + 可能追问”输出。
* 语气：口语化、适合面试现场，不要像论文。

## 5.3 典型 Prompt 模板

### 事实查询类

```text
你是AI求职面试助手。请根据以下题库内容回答用户问题。
要求：
1. 优先依据题库内容，不要凭空编造。
2. 如果题库没有明确答案，请说明“资料不足”。
3. 输出结构为：简短结论 + 详细解释 + 面试表达建议。

题库内容：
"""
{retrieved_context}
"""

用户问题：
{user_question}
```

### 数据分析类

```text
你是数据分析面试助手。请根据SQL或Python统计结果进行解释。
要求：
1. 不要生成未提供的数据。
2. 先总结核心发现，再解释可能原因，最后给业务建议。
3. 如果数据样本不足，需要提示局限性。

统计结果：
{data_result}

用户问题：
{user_question}
```

### 面试模拟类

```text
你是面试官。请根据候选人简历和目标岗位提出一个问题。
要求：
1. 问题要贴近岗位能力。
2. 每次只问一个问题。
3. 根据候选人回答给出优点、问题和改进建议。
4. 如果回答过于泛泛，要追问项目细节、技术选型或量化结果。

候选人简历：
{resume}

目标岗位：
{target_role}

已回答内容：
{history}
```

## 6.3 SQL 与 Python 的选择逻辑

可以回答：

> 如果是结构化数据的筛选、聚合、分组、排序、连接，我会优先用 SQL，因为 SQL 更适合直接在数据库层完成统计，效率高、口径清晰、便于复现。比如统计不同城市 AI 岗位数量、不同岗位平均薪资、某个专业对应岗位分布，我会用 SQL。
> 如果涉及复杂清洗、文本处理、机器学习、可视化、相关性分析或多步骤建模，我会用 Python。例如清洗岗位描述文本、提取技能关键词、做薪资分布图、训练简单分类模型、计算相似度等。
> 在实际项目中，我通常会先用 SQL 得到干净的统计结果，再用 Python 做进一步分析和可视化，最后把结果传给大模型进行解释。

## 6.4 面试官追问

* 你如何保证指标口径一致？
* 如果数据量很大，SQL 查询慢怎么办？
* Python 数据清洗时如何保证结果可复现？
* 你如何向非技术同事解释数据结论？

# 十四、AI 求职面试助手的追问规则

## 14.1 追问逻辑

当候选人回答较泛时，追问：

* 你具体负责哪一部分？
* 你用了什么技术？
* 为什么这么选型？
* 有没有遇到问题？
* 如何解决？
* 最终效果如何？
* 有没有量化指标？
* 如果重做会怎么优化？

当候选人回答技术点但缺少业务价值时，追问：

* 这个功能解决了什么用户问题？
* 为什么这个指标重要？
* 业务方如何使用你的结果？
* 用户反馈如何？

当候选人回答项目成果但缺少可信度时，追问：

* 数据来源是什么？
* 样本量是多少？
* 指标怎么计算？
* 有没有对照组？
* 是否可能有其他因素影响结果？

## 14.2 评分标准

每次回答可以按 5 个维度评分，每项 1–5 分：

1. 结构清晰度：是否有背景、行动、结果。
2. 岗位匹配度：是否体现目标岗位能力。
3. 技术细节：是否说明工具、流程、选型和实现。
4. 量化结果：是否有数据或可验证结果。
5. 复盘意识：是否说明问题、改进和下一步计划。

总分建议：

* 22–25 分：优秀，回答完整，有细节和量化结果。
* 18–21 分：较好，结构清楚，但细节或数据不足。
* 14–17 分：一般，有基本回答，但偏泛。
* 10–13 分：较弱，缺少项目细节和个人贡献。
* 10 分以下：需要重构回答。
